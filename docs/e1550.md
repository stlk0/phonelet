# Modem notes for chan_dongle (Huawei E1550 reference)

Phonelet targets Huawei voice-capable 3G USB modems compatible with `chan_dongle`; only the E1550
(firmware 11.608.13.02.00) has been tested on hardware. The ME storage state machine is designed
around that firmware and one SIM (see the [patch notes](../chan_dongle_patch/README.md#me-storage-state-machine));
findings below may not hold for another modem, SIM or firmware. Some conclusions
describe firmware behaviour; they are not all hardware-tested guarantees. No permanent cause or
fix for registration loss has been established.

These notes are useful beyond Phonelet, but the SMS recovery behaviour described below requires
the [Phonelet chan_dongle patches](../chan_dongle_patch/README.md).
For deployment and maintenance, see [Installation](install.md) and [Operations](operations.md).

## First setup

Disable the SIM PIN in a phone before inserting the SIM. The pinned chan_dongle queries
`AT+CPIN?`; on `+CPIN: SIM PIN` it logs that a PIN is needed and returns an error.
It has no PIN setting or automatic PIN entry. A SIM requesting PUK also reports an error.

With the host powered off, fit the SIM and connect the modem. Arrange stable USB names before
starting chan_dongle. Keep other serial-port managers, including ModemManager, away from these
ports while chan_dongle owns them. Send commands through the driver when it is running; do not
open the same port with a second terminal program.

`AT^U2DIAG` values are model-specific: `0` selects modem-only mode on the E1550, removing the virtual CD-ROM/card-reader
functions and exposing the required serial interfaces. This is a persistent configuration change,
not a recovery command. Plan for USB re-enumeration and recheck the interface mapping afterwards.

A new modem may first enumerate as a CD-ROM (USB ID `12d1:1446`) with no `ttyUSB` ports. The
Debian package `usb-modeswitch` switches it to modem mode, after which `AT^U2DIAG=0` can be sent.
This project has not verified this step on hardware.

Check voice support before relying on calls. chan_dongle uses the query `AT^CVOICE?`;
the expected response starts with `^CVOICE: 0` when voice is enabled. An `ERROR` leaves voice
capability unconfirmed. A command response alone does not verify a conversation: check both directions of
audio with an actual call during installation. Avoid generic unlock/reset tools: a reset has
disabled the voice feature on this modem, and another firmware image was not recognised correctly
by Linux.

## Port mapping and stable names

`AT^GETPORTMODE` reports the expected mapping as `MDM:0,DIAG:1,PCUI:2`:

| USB interface | Role | chan_dongle / `.env` setting | Stable name used by Phonelet |
| --- | --- | --- | --- |
| `00` | Modem (MDM, unused by Phonelet) | Not opened by the driver | `/dev/dongle0-modem` |
| `01` | Audio (also labelled DIAG) | `audio=` (`AST_DONGLE_AUDIO`) | `/dev/dongle0-audio` |
| `02` | PCUI: AT replies and unsolicited notifications | `data=` (`AST_DONGLE_DATA`) | `/dev/dongle0-at` |

Use **PCUI for `data=`** (`AST_DONGLE_DATA=/dev/dongle0-at`). In normal command mode,
incoming-call and SMS notifications reach PCUI; getting AT replies on MDM does not establish that
incoming events reach that port. `/dev/dongle0-at` is the driver's `data=` port (replies and
notifications together), while `/dev/dongle0-modem` is the unused modem (MDM) port.
There is no separate `urc=` setting in Phonelet's patch set. Keep interface `01` dedicated to voice.

Do not assume that `ttyUSB0`, `ttyUSB1` and `ttyUSB2` retain their roles after a reboot or when
another USB serial device is connected. Match the USB ID and **interface number** in udev rules
on the host. For this single-modem mapping, `/etc/udev/rules.d/99-phonelet-modem.rules` can contain:

```udev
SUBSYSTEM=="tty", ATTRS{idVendor}=="12d1", ATTRS{idProduct}=="1001", ENV{ID_USB_INTERFACE_NUM}=="00", SYMLINK+="dongle0-modem"
SUBSYSTEM=="tty", ATTRS{idVendor}=="12d1", ATTRS{idProduct}=="1001", ENV{ID_USB_INTERFACE_NUM}=="01", SYMLINK+="dongle0-audio"
SUBSYSTEM=="tty", ATTRS{idVendor}=="12d1", ATTRS{idProduct}=="1001", ENV{ID_USB_INTERFACE_NUM}=="02", SYMLINK+="dongle0-at"
```

Verify each link against the USB interface before starting the driver. These names give:

```ini
[dongle0]
data=/dev/dongle0-at
audio=/dev/dongle0-audio
```

## Using another chan_dongle modem

For another Huawei voice-capable 3G USB modem compatible with `chan_dongle`, verify these steps;
only the E1550 (firmware 11.608.13.02.00) has been tested on hardware.

1. Check for serial ports with `ls /dev/ttyUSB*`; `lsusb` alone also finds CD-ROM mode. Before
   installing Phonelet, use a serial terminal (such as `picocom` or `minicom`) on PCUI to query `AT^CVOICE?`.
2. Confirm which USB interface numbers carry **Audio** and **PCUI** (`AT^GETPORTMODE` and `dmesg` /
   `udevadm info`).
3. If the interface layout matches `00=MDM, 01=Audio, 02=PCUI`, pass
   `PHONELET_BOOTSTRAP_MODEM_USB_ID=12d1:<pid>` to `install.sh` (see
   [Optional bootstrap settings](install.md#optional-bootstrap-settings)).
4. Phonelet expects `00=MDM, 01=Audio, 02=PCUI`: bootstrap rewrites `99-phonelet-modem.rules` on
   every first-install run. Another layout needs changes to `scripts/bootstrap.sh` and the MDM guard in `scripts/deploy-release.py`.
5. Verify both directions of calls and multipart SMS, and check the logs for whether `"ME"` SMS
   storage succeeded or fell back to `"SM"`.

## SMS storage: ME and SM

`SM` means SIM storage; `ME` means modem storage. On the tested combination, the SIM sometimes
returned a storage error for a final multipart SMS fragment even though its contents could be
read back. The modem could then reject reception and the network might retry late or stop retrying.
Selecting ME avoids this particular SIM write path. It does not solve every possible SMS failure.

`AT+CPMS` has three distinct parameters:

| Parameter | Meaning |
| --- | --- |
| `mem1` | Storage used for reading and deleting messages |
| `mem2` | Storage used for writing messages |
| `mem3` | Destination for new incoming messages |

Phonelet's driver selects `AT+CPMS="ME","ME","ME"` during initialisation. To read SIM messages it
then selects `AT+CPMS="SM"`, changing **only `mem1`**; reception continues into ME. It returns to
ME for reading afterwards. Changing all three parameters to SM would move new reception back to
the SIM and could leave that route in effect after a failure. The receive route persists across
power cycles on this firmware; read/write selections return to SM after power-on or ATZ.
Let the driver manage these selections instead of changing them underneath it.
If ME selection is rejected, Phonelet warns and falls back to SM; check the logs to confirm which
storage is in use.

The same slot number in ME and SM denotes different messages. A notification such as
`+CMTI: "ME",7` must be handled with ME selected for reading. The patched driver reads both
storages at initialisation and periodically when idle, because some special message categories
can still land on the SIM. It journals and fsyncs each fragment before deleting the source slot.
An unpatched chan_dongle does not provide that journal-before-delete guarantee.

Observed capacity was 23 slots in ME and 15 on the SIM, numbered from zero. When ME fills, the
modem reports full memory to the network; it does not spill ordinary messages over to the SIM.
Later network retries depend on the sender's service centre and message expiry. Monitor available
space. **Survival of ME contents after power removal has not been verified on hardware.**

An SMS read error is **not proof of corruption and never a reason to delete messages**. Preserve
logs, the reception journal and a database backup first. Check the selected storage, driver
contract and deduplicated rereading. If extraction still fails, preserve the original state for
diagnosis. Bulk deletion is not a recovery procedure.

## Registration loss and recovery

A modem can still answer AT commands over USB while it has lost useful radio reception.
Before changing anything, preserve the original failure state and check registration, signal,
network availability and SIM status. `AT+CREG?`, `AT+CSQ` and `AT+COPS?` provide basic observations;
a successful reply is not proof that calls or SMS work. A SIM failure response can point to the
SIM or its contacts, but does not establish a root cause.

For the observed persistent registration failure, AT resets (`AT+CFUN=0/1`, `AT+CFUN=1,1`) and
forcing 2G did not restore service. Software USB deauthorisation/re-authorisation also failed;
it reconnects interfaces and does not establish that modem power was removed. A host reboot did
not reliably help. A cold power cycle of the modem did restore registration in one case. That
result is neither a permanent fix nor proof that all registration failures share a cause.
Changing network preference has not been proven to prevent recurrence.

**Physical hot-unplug has hung some hosts, even after software USB deauthorisation. Power the
host down before touching the modem or SIM.** For a cold start, shut the host down, remove modem
power for at least 60 seconds, then reconnect and start the host. A reboot with USB power still
present is not a cold power cycle. Preserve pending messages and journals before intervention;
check registration and reception afterwards. Do not automate a chain of resets.

## Commands never to send

- **`AT^PORTSEL` in any form**, including query and test forms. It is not a way to move
  notifications onto MDM. On this firmware it can suppress unsolicited notifications and retain
  their buffers until restart, risking buffer exhaustion.
- **`AT+CFUN=4`**. It puts the modem into an offline state that requires a reset to leave.
- **`AT+COPS=?` and `AT+CPOL?`** through chan_dongle. These slow queries can exceed the driver's
  timeout and trigger modem reinitialisation. The operator query `AT+COPS?` is a different command.

A command described as a query can still disrupt service. Do not copy generic modem reset,
port-selection or network-scan recipes into monitoring or automatic recovery.

## Power supply

Allow for short transmit-current peaks, not just idle consumption. Use an adequate host supply
and a sound USB power path; avoid long, thin cables and overloaded unpowered hubs. A modem
enumerating successfully over USB does not prove the supply remains stable while transmitting.
Power problems are a diagnostic possibility, not an established explanation for every radio
failure. Software resets cannot substitute for actually removing power.

## Voice gain

chan_dongle's gain values are sample multipliers, not decibels. `rxgain` affects modem-to-SIP audio;
`txgain` affects SIP-to-modem audio. Values from `-1` to `1` leave samples unchanged. A positive
value above `1` multiplies them; a negative value below `-1` divides by its absolute value.
For example, `3` means times three (about +9.5 dB), with clipping when samples exceed the range.

Raising both directions can amplify residual echo and cause clipping. The SIP phone may already
apply automatic gain and echo cancellation before `txgain` adds more gain. Removing transmit
amplification (`txgain=0`, with `rxgain=3` retained) improved perceived sound in this installation;
these are not universal settings or a measured guarantee of audio quality. Start without extra
gain and adjust only after checking both sides of a conversation. Audio delay and its allocation
between the modem, network and SIP client have not been measured.
